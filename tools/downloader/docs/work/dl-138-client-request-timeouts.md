# dl-138 — A probe or job request that never settles holds its slot

## Why

dl-133 (PR #781, branch `downloader/dl-133-one-box-per-analysis`, `ready` on main and not merged) gives each analysis its own box. The page counts its probes against the server's per-client probe cap (2 at once, `maxProbesPerClient`, `api/src/config.ts`), and its jobs against the job cap (2 in flight, `maxJobsPerClient`). For a closed analysis, the owner chose to count its probe POST until the POST settles, because the server holds its probe slot until its handler ends: `clientReleaseProbe` is released in the handler's outermost `finally` (`api/src/routes/probe.ts`). The job count is the page's own. The server takes no job slot at `POST /api/jobs`, which writes a `queued` row and hands back a link; the slot is taken when the link is opened (`api/src/routes/jobs.ts`, `routes/files.ts`, `jobs/links.ts`). Both counts assume that a request settles. On main, `request()` in `tools/downloader/web/src/api/http.ts` passes `fetch` no timeout and no abort signal, and `ApiClient.probe` and `ApiClient.createJob` both go through it, so a request that stalls keeps its count for the life of the page.

Gate 2 of dl-133 found two cases, both `low`, and neither has a live call site:

- **N2, probe.** Two running analyses were closed while their probe POSTs were out, and those POSTs never settle. The count stays at 2 for the life of the page, and every later analysis waits. `ApiClient.probe` also spans the human-check wait before the POST (`withHumanCheck`, awaited before `request()` is called), which holds no server slot, so the count over-holds there. That is the safe direction.
- **N3, createJob.** A `createJob` that never settles leaves its box `starting`. Download, Analyse again and Dismiss are all disabled, and the box keeps its job count (`jobsInFlight`, `web/src/lib/boxes.ts`, which counts a `probed` box whose download is `starting`). dl-133's gate 1 F2 fix disabled Analyse again while the job is being created, which removed the box's only way out.

Both have one cause: no client-side request timeout. Their remedies differ, so the choice is held open in the Decision below.

**Reproduction.** Gate 2's probe (`gate-dl133-g2-probe.test.tsx`, cases `(o2)` and `(n3)`) is in a session scratch directory and is not committed. It is reference only, and no `Done when` line depends on it. Each case drives the real `App` with a mocked `ApiClient` under fake timers, advances 30 minutes, and reads the page. The filer re-ran it at dl-133's head `1042c0c6`, which is not the `4c621dc8` that gate 2 read: the branch has moved on since. Both shas are named as the readings' provenance only; a squash merge of PR #781 strands them, and no line below pins either. Its lines, which gate 1 re-ran and got again:

- `(o2)` 30 min with two orphans out and two boxes waiting: `probe calls 2; headings Waiting | Waiting`
- `(o2)` three new analyses on a settled page: `started 2 of 3`, once the orphans have settled
- `(n3)` 30 min after Download with createJob unsettled, buttons in the box: `Starting…:true | Analyse again:true | Dismiss:true; createJob calls 1`

The probe replaces `ApiClient` with a fake, so it never reaches `request()` and cannot show a timeout. Its `(o2)` case also asserts the wedge (`expect(calls(fake)).toBe(2)`) before its later steps, so it cannot read a fix at all. A fix is graded by the committed App-level cases and `ApiClient`-level tests named in Done when.

## Decision — open

Question 1 is settled. Questions 2 and 3 are open. The recommendations are the filer's; the choices are the owner's.

**Question 1 — answered 2026-11-10 by the owner.** Record N2 and N3 only, or file a ticket. Options: record only (recommended by the orchestrator); file a ticket. Chosen: file a ticket. This ticket is that filing.

**Question 2 — open.** The remedy for N2, `ApiClient.probe`.

- **(a) A timeout on the POST, with a bound the owner names.** The timer starts at the fetch, after `withHumanCheck`, so the human-check wait on the page is not counted. The bound must clear the longest the server can take to release its probe slot, measured from that same moment, or the count gives the slot back while the server still holds it: F1's mismatch again. **The floor is measured from the fetch and includes the waits before the slot is taken**, because the slot is not taken at the fetch. In `routes/probe.ts` the handler first awaits `humanCheck.require` (the siteverify, bounded at `SITEVERIFY_TIMEOUT_MS`, 5 s, `api/src/human-check.ts`, when the check is on; whether the live deployment has it on was not checked), then `guard.assertAllowed` (one `dns.lookup`, `ssrf.ts`, with no bound in the code read), then reads the cache, and only then calls `probeClientGate.tryAcquire`. The slot is then held through `registry.resolve` (`probeTimeoutMs`, 45 s by default, `PROBE_TIMEOUT_CEILING_MS` 50 s, `config.ts`), then `guard.assertAllAllowed` (the vet of the resolver's output: it runs before the frame grab, and it runs one lookup per distinct URL concurrently, none bounded in the code read), then `captureThumbnail`, whose frame grab is bounded at `FRAME_GRAB_TIMEOUT_MS` (6 s, `thumbnails.ts`). It is released in the handler's outermost `finally`. By arithmetic from the code, not measured: the slot is held about 51 s at the default and about 56 s at the ceiling, plus the vet's lookups; from the fetch, add the siteverify's 5 s and `assertAllowed`'s lookup, which makes the release as late as about 56 s at the default and about 61 s at the ceiling on a deployment with the check on, plus the two sets of unbounded lookups. A bound of 60 s therefore clears the default but not the ceiling. `probeTimeoutMs` is the resolution chain's budget, not the whole hold, and the page cannot read the deployment's value: `clientConfigResponseSchema` carries only `humanCheck` (`contract/src/api.ts`). The owner names the bound and its margin over those figures. A settled POST is what dl-133's count rule expects, so the rule does not change. Recommended: the smaller change, inside the count rule the owner chose. Costs: after a closed analysis, a count can be held up to the bound; and the floor cannot be checked from the page, only by the owner's judgement. Also to name: whether the timeout goes in `request()`, so `getJob` and `cancelJob` are bounded too, or on the two calls only; and whether the timeout aborts the fetch or only stops waiting on it. **Unmeasured (gate 2's direction, the server not run):** if the timeout aborts the fetch, the socket closes and the server's slot frees only when its handler unwinds, as under (b), so a bound below the floor leaves the same window and the floor is not a hard limit; and the handler registers its `close` listener after the siteverify, the lookup and the cache read (see (b)), so an abort in that first phase may not shorten the hold.
- **(b) An abort signal on `ApiClient.probe`, aborted when the analysis is closed.** This is the option dl-133's F1 passed over. It needs no bound to name, and the orphans N2 describes all come from closing or re-analysing an analysis whose POST is out, so an abort on close covers them. It frees the client's count at once. The server's slot frees only when its handler unwinds after the socket closes (`routes/probe.ts` aborts its controller on `request.raw` close, and `assertAllAllowed` takes no signal), so a window remains in which a third analysis could be refused `RATE_LIMITED`, the F1 symptom. **Unmeasured (gate 1's phrase "a short window" and gate 2's direction, the server not run):** the `close` listener is registered after the siteverify, the SSRF lookup and the cache read, so a close in that first phase may never abort the controller, and the probe then holds its whole budget; how long the window is was not measured. Costs: it reopens F1, which the owner decided against this option, and it touches `api/types.ts`, `web/src/api/http.ts`, `mock.ts` and `useBoxes`. Also to name: whether a waiting box starts at once when the count frees (and can meet `RATE_LIMITED` inside the window) or waits for a release the page cannot read, which would be a modelled delay or a count held past the abort, and so a change to (b) as worded. Done when 3 reads the answer.

**Question 3 — open.** The remedy for N3, `createJob`.

- **(a) A timeout on `createJob`, with a bound the owner names.** A timed-out `createJob` leaves one `queued` row that nothing opens. The page's `useJobs.start` throws before `attach`, so `openLink` is never called and no box is re-created. The row takes no job slot, because the slot is taken at the link's `GET` (`routes/files.ts`). The sweep cancels an unopened row as `link-expired` after the 15-minute link TTL (`LINK_TTL_MS`, `jobs/links.ts`; `runSweep` in `server.ts` runs every `gcIntervalMs`, 60 s by default). The row spends one token of the per-minute `POST /api/jobs` limiter. The box shows the request's error (`request()` maps a failed fetch to `UNREACHABLE`), and its buttons are enabled again. The bound must clear the POST's own waits: the human-check siteverify is bounded at 5 s (`SITEVERIFY_TIMEOUT_MS`, `api/src/human-check.ts`), and the SSRF guard's `dns.lookup` (`api/src/ssrf.ts`) has no bound in the code read. Recommended. Costs: a visitor who retries after the failure leaves a second queued row, and the owner's bound carries the margin over the POST's waits.
- **(b) Dismiss enabled while the job is being created, and a late answer for a dismissed box guarded before `attach`.** The box has an exit at once. Costs: it reverses the rule that dl-133 keeps, that Dismiss is disabled while a job is created (`ProbePanel.tsx`: "the box is about to become that job"), and the committed test that asserts it, `web/test/probe-panel.test.tsx` › "an analysis is dismissed from its own panel, except while its job is being created (dl-133)", which a build of (b) must rewrite (its sibling › "Analyse again waits while the job is being created, as Dismiss does (gate 1 F2)" asserts Analyse again, which (b) as worded leaves disabled). The guard must sit before `attach` in `useJobs.start` (`web/src/hooks/useJobs.ts`) and `useBoxes.startDownload`, so that `openLink` and `openJobEvents` are not called and no box appears. Without it, a dismissed box is re-created and its download starts (gate 1's plant of Dismiss without the guard: `boxes 2 -> 3; openLink calls 1; openJobEvents calls 1`). Its last cost is what (b) alone does not end: a `createJob` which never answers leaves its request pending with the box already dismissed. There is no job to cancel, and a late answer is what the guard covers; the page's count has fallen with the box, and the server holds no job slot for the POST. Under (a) that request is the one the timeout bounds.

Either option, or both, can be taken; the answer names which.
