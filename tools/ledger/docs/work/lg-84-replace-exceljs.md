# lg-84 — Replace exceljs

## Why

`exceljs` is the only thing in the ledger that opens a spreadsheet:
`tools/ledger/api/src/xlsx.ts` reads a workbook's cached cell values and formula
text for `@ledger/books` (lg-7). Its last release is 4.4.0, from 2023, and its
dependency chain (`archiver`, `zip-stream`, `readdir-glob`,
`unzipper → fstream → rimraf`) pins glob 7 with minimatch 3 and minimatch 5. Those carry
GHSA-g3hv-75wg-m249, which is fixed only in minimatch 11, a major that glob 7
cannot load. Of the 9 moderate entries `npm audit` reported on 2026-10-31, six
are exceljs and its chain (`exceljs`, `archiver`, `archiver-utils`,
`zip-stream`, `readdir-glob`, `rimraf`), and `glob` and `minimatch` are shared
with `@fastify/static`. **repo-134** records the full account and why no code here
runs the bug. The package also needs a root `overrides` entry to force uuid 11
over its pinned uuid 8 (`package.json`'s `// overrides`).

The owner chose on 2026-10-31 to replace it rather than record the advisories and
wait. No exceljs release is likely to clear the chain, so the replacement is the
only way out.

## What the replacement must keep

`xlsx.ts`'s behaviour, which `test/xlsx.test.ts`, `test/statements.test.ts`,
`test/workbook-describe.test.ts` and `test/layout/` pin:

- every sheet, in workbook order, by name, as rows of cells, with empty rows and
  cells kept as gaps;
- a cell's **cached** value, never an evaluated one, as number, text or date (a
  date being a UTC calendar day). Rich text is joined, an error cell reads as its
  error text, and a cached `0` or `FALSE` is a value, not an absence (exceljs drops
  falsy results from `cell.value`, which is why `xlsx.ts` reads `cell.model`);
- a formula cell's formula text beside its value, shared formulas included,
  because a period's settlement formula is told apart by it;
- a merged range read only at its first cell;
- an unreadable file raises `BAD_REQUEST` naming the reader's reason.

`workbook-zip.ts` (lg-66) runs before the reader and stays. It already checks
the zip's central directory and bounds the inflated size with `node:zlib`, so a
replacement need not repeat that.

**The tests write workbooks with exceljs too** (`test/helpers/workbook.ts`,
`test/helpers/xlsx-file.ts`, `test/xlsx.test.ts`). Keeping exceljs as a
devDependency for them leaves the lockfile, and therefore `npm audit`, exactly
where it is. So the writer has to go as well.

## Decision — answered

**Answered 2026-11-01 by the owner: what reads the workbook? SheetJS from its
own CDN (3).** Chosen from three options: a reader of our own on `node:zlib`
and `fast-xml-parser`, the same without an XML library, and SheetJS. Option 2
was checked before asking and dropped: `read-excel-file` 9.3.12 returns
`[type, value]` per cell with no formula text, its merge code is commented out,
and its README says an error cell reads as empty.

1. **A reader of our own on `node:zlib` and an XML parser.** `workbook-zip.ts`
   already walks the central directory and inflates entries. What remains is
   parsing `xl/workbook.xml`, `xl/_rels/workbook.xml.rels`, the sheets,
   `sharedStrings.xml` and, for dates, `styles.xml` number formats. The new
   dependencies would be one XML parser (for example `fast-xml-parser`) or none.
   This is the most code to own, and date detection from number formats is the
   subtle part.
2. **`read-excel-file`** (9.3.14, published 2026-10-29, maintained). It is small,
   but whether it exposes formula text beside a cached value, and merges, is
   unverified. Check that first. It may not keep what the list above requires.
3. **SheetJS from its own CDN.** lg-7 refused it because the registry copy (`xlsx`
   0.18.5) is stale and carries advisories, and fixed builds ship only off the
   registry. Choosing it reverses lg-7's choice and takes on a non-registry
   tarball, which the seven-day rule and `npm audit` do not cover.

**Answered 2026-11-01 by the owner: what writes the test fixtures? SheetJS
too**, asked as "can you use sheetjs to write test files?" against (a) and (b)
below. Measured before building: it writes every kind of cell the reader's
tests need but two, rich text and a shared formula, which `xlsx.test.ts`
splices into the sheet's XML through the helpers' own `zipOf`.

The options it was asked against: Either (a) a minimal writer in the test
helpers (zip via `node:zlib` deflate-raw plus hand-built XML, which is easy if
option 1 is chosen because the formats are already understood), or (b)
committed `.xlsx` fixtures under `test/fixtures/`, regenerated by a script kept
out of the lockfile. (b) loses the helpers' ability to build a workbook from a
table inside the test.

## Build

1. `xlsx` 0.20.3 from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz` in
   `@ledger/api`'s `dependencies`; `exceljs` and the root `overrides.exceljs`
   with its `// overrides` comment removed. `npm audit` read before and after.
2. `xlsx.ts` reads through `XLSX.read` (dense, formulas, number formats) and
   keeps every behaviour listed above.
3. `test/helpers/xlsx-file.ts` gains a `SheetWriter` and `workbookOf`, which
   `xlsxOf`, `render()` and `xlsx.test.ts` build with.
4. `workbook-zip.ts`'s bounds re-checked against SheetJS: its memory per MiB,
   and which entries and sizes its zip walk reads.

## Done when

- `exceljs` is absent from `package-lock.json`.
- `npm audit` reports no advisory through the ledger. What repo-134 tracks for
  `@fastify/static` may remain.
- `npm test -- --project ledger` passes. The reader's tests keep their
  assertions, and only how they build a workbook changes.

    repo-134's.
  - **What the brief did not know.** `XLSX.read` reads bytes that are not a zip
    as a one-sheet CSV with no error, so `xlsx.ts` refuses any `bookType` but
    `xlsx` and `xlsm`. A formula with no saved result reads as `t: "e"` with no
    value, which `xlsx.ts` reads as no value. An error cell's text exists only
    with SheetJS's cell text on, so it stays on. Dates are read from the number
    format with `SSF`, timezone-free, `date1904` honoured.
  - **The bounds.** SheetJS cost +56 to +68 MB for a sheet just under 4 MiB, where
    `exceljs` cost +98 to +109 MB. Its zip walk follows the end record's count
    through the central directory as `workbook-zip.ts` does. It takes the method
    from the local header, but inflates into a buffer of the declared size and no
    more, measured: a sheet inflating to 35 178 290 bytes declared as 1 000 was
    read as 1 000 bytes. `workbook-zip.ts`'s header says so, and that it holds
    only while nothing calls `XLSX.set_zlib`.
  - **Tests.** `npm test -- --project ledger`: 97 files, 2039 passed. The
    reader's assertions are unchanged; only how the workbook is built is.
  - **Fold-in.** Comments naming `exceljs` as the reader in `workbook-zip.ts`,
    `workbook-describe.ts` and two test names now name the reader; measurements
    taken under `exceljs` keep its name. The contract's comment on fixture sizes
    "as `exceljs` writes them" is left: still true of the measurement, and the
    contract is not this ticket's to edit.
